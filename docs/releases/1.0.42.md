# SuperCli 1.0.42

Faster and steadier on big, busy projects: no more leftover git processes,
far less disk and memory use with many workers, work that survives a
network change, and reports that are never missed. Polish notes follow the
English ones.

## Before updating

- Back up your portable `supercli-data` directory and close other running
  copies before installing. The updater replaces the two executables, not
  private data, and a manual restart is required afterward.
- On start, SuperCli ends git processes that an earlier version left
  running for its own checkpoint store (only those: never your own git).
- No configuration changes are required. New optional setting:
  `network_wait_minutes` (default 10).

## Performance

- Git processes no longer outlive their command: on Windows a cancelled
  checkpoint snapshot left the real git running with no parent (seen: 136
  processes, 40% CPU, 3.6 GB). Every git SuperCli starts now runs in a
  kill-on-close job, so a cancel, a timeout or closing SuperCli ends it.
- Huge workspaces: a whole-workspace snapshot that does not fit its time
  budget is remembered for the workspace (re-checked after 6 hours) instead
  of being retried on every command, with one notice per turn.
- Worker lists no longer read every worker's saved conversation: with 400
  workers one status poll went from 12 s and 3.3 GB read to about 2 ms.
- History: scrolling back always reaches the first message, also while a
  run is shown; live refreshes fetch only the newest turn, keep the pages
  you loaded and your reading position.
- Verify commands, user tools, `search_code` (2-minute limit) and card
  clocks no longer keep running after they are no longer needed.

## Workers and runs

- A report that arrived while the coordinator was answering is named in
  the next turn as new, so it is never treated as already handled.
- A long coordinator command moves to the background after 2 minutes
  whenever workers of the conversation are running, also workers started
  by an earlier turn.
- `process_session wait` returns after 15 minutes at most, and earlier with
  "process looks hung" when there is no output and no CPU use.
- A worker stopped by its run time limit says so and how to continue.
- Network change (cable to Wi-Fi): a model call waits for the network for
  up to 10 minutes and sends the request again; text shown before the drop
  is not repeated and tool calls never run twice. The status line and the
  worker card show "No connection — waiting for the network (0:42)…". If
  the network does not return, the run stops as a resumable network stop.
- Rewind and "Edit AI reply" wait only for the conversation's own work;
  another running conversation, in this project or another, no longer
  blocks them. A file rewind asks only when its files overlap a running
  conversation ("Rewind conversation only", "Rewind anyway", "Cancel").
- Clicking a worker in the panel above the chat loads its card if needed,
  opens it and keeps it open.

# SuperCli 1.0.42 (PL)

Szybciej i stabilniej w dużych, zajętych projektach: koniec z porzuconymi
procesami git, dużo mniej odczytów dysku i pamięci przy wielu workerach,
praca przetrwa zmianę sieci, a raporty nie giną.

## Przed aktualizacją

- Zrób kopię katalogu `supercli-data` i zamknij inne uruchomione kopie.
  Aktualizator wymienia dwa pliki wykonywalne, nie dane; potem uruchom
  program ponownie.
- Przy starcie SuperCli kończy procesy git, które poprzednia wersja
  zostawiła dla własnego magazynu checkpointów (tylko te, nigdy Twój git).
- Konfiguracji nie trzeba zmieniać. Nowe, opcjonalne ustawienie:
  `network_wait_minutes` (domyślnie 10).

## Wydajność

- Procesy git nie przeżywają już swojej komendy: na Windows przerwany
  snapshot checkpointu zostawiał prawdziwego gita bez rodzica (było 136
  procesów, 40% CPU, 3,6 GB). Każdy git uruchamiany przez SuperCli działa
  teraz w zadaniu zamykanym razem z nim.
- Ogromne projekty: snapshot całego projektu, który nie mieści się w
  limicie czasu, jest zapamiętywany (ponowna próba po 6 godzinach) zamiast
  powtarzania przy każdej komendzie; jedno ostrzeżenie na turę.
- Lista workerów nie czyta już całych zapisanych rozmów: przy 400 workerach
  jedno odświeżenie statusu spadło z 12 s i 3,3 GB odczytu do ok. 2 ms.
- Historia: przewijanie zawsze dociera do pierwszej wiadomości, także w
  trakcie pracy; odświeżenia na żywo pobierają tylko najnowszą turę i
  zachowują wczytane strony oraz miejsce czytania.
- Komendy weryfikacji, narzędzia użytkownika, `search_code` (limit 2 min) i
  zegary kart nie działają już dłużej, niż trzeba.

## Workerzy i przebiegi

- Raport, który przyszedł, gdy koordynator odpowiadał, jest w następnej
  turze wymieniony jako nowy — nigdy nie uchodzi za obsłużony.
- Długa komenda koordynatora przechodzi w tło po 2 minutach, gdy działają
  workerzy rozmowy, także uruchomieni we wcześniejszej turze.
- `process_session wait` wraca najpóźniej po 15 minutach, a wcześniej z
  „proces wygląda na zawieszony”, gdy nie ma wyjścia ani użycia CPU.
- Worker zatrzymany limitem czasu przebiegu mówi o tym i jak kontynuować.
- Zmiana sieci (kabel na Wi-Fi): wywołanie modelu czeka na sieć do 10 minut
  i wysyła prośbę ponownie; tekst sprzed zerwania się nie powtarza, a
  narzędzia nie uruchamiają się dwa razy. Pasek stanu i karta workera
  pokazują „Brak połączenia — czekam na sieć (0:42)…”. Jeśli sieć nie
  wróci, przebieg zatrzymuje się jako wznawialny stop sieciowy.
- Cofanie i „Edytuj odpowiedź AI” czekają tylko na pracę tej rozmowy; inna
  działająca rozmowa (w tym lub innym projekcie) ich nie blokuje. Cofanie
  plików pyta tylko przy wspólnych plikach z działającą rozmową („Cofnij
  tylko rozmowę”, „Cofnij mimo to”, „Anuluj”).
- Kliknięcie workera w panelu nad czatem wczytuje jego kartę w razie
  potrzeby, otwiera ją i zostawia otwartą.
