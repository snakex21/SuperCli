# SuperCli 1.0.23

Risky mail and file operations now wait for your approval in SuperCli itself,
the Thunderbird tool is harder for local models to misuse, and a set of fixes
found with a new agent eval suite makes edits and final answers more honest.

## Before updating

- Back up your portable `supercli-data` directory and close other running copies
  before installing. The updater replaces the two executables, not private data,
  and a manual restart is required afterward.
- Batch runs (`--batch`, SuperBot, scripts) that used Thunderbird or Outlook
  mail writes, or `trash` outside the workspace, are now refused unless you
  allow them (see "Approvals" below). Image/video generation and
  `headless_control` changes were already refused in batch runs; they can now
  be allowed the same way.

## Approvals for risky actions

- **The host decides, not the model.** Tools declare a risk level per
  operation (read, reversible write, destructive, external side effect). Every
  `thunderbird_mail` write (folders, copy, move, import, trash, restore, purge,
  empty Trash, address books and contacts), `outlook_mail` trash/purge and
  `trash` of a path outside the workspace waits for your answer before it runs.
  The same gate now also covers the tools that used the older one-off "Allow
  once" prompt: `headless_control` actions that change a VM or browser
  session (open, navigate, click, type, keys, close), `generate_image` /
  `generate_video` (a paid request to the configured provider) and
  `host_power` arm. They get the same card, audit log, allowlist and batch
  deny-by-default, are never offered "approve similar", and run only under an
  approval bound to the exact arguments (or goal) you saw.
  A `confirm` value sent by the model is discarded; SuperCli sets it only after
  you approve. None of the newly gated tools has a confirmation argument at all.
  Ordinary edits inside the workspace are not gated.
- **GUI**: an approval card in the chat shows the operation, account, folder,
  destination, message count and a few senders/subjects (never message
  bodies), and whether it can be undone. Approve, Deny, or Approve similar in
  this session. Keyboard accessible, Esc denies, translated into all UI
  languages in both the GUI and the TUI (the TUI prompt used to know only
  English and Polish).
- **TUI**: the same details with `y` approve, `n`/Esc deny, `a` approve similar.
- **Approve similar** covers the same tool, operation, account, folder and
  destination for 30 minutes (`session_grant_minutes`) and is never offered for
  irreversible operations.
- **Batch and non-interactive runs deny by default** with a clear tool error.
  Allow narrow scopes with `[approvals] auto_approve` in the global
  `<data-dir>/config.toml` (project configs cannot pre-approve), for example
  `"thunderbird_mail:copy:account2"` or `"generate_image:generate:openai"`.
  The explicit `--allow-all` flag of a
  batch run approves every gated action; this is risky and documented as such.
  `allow_all` in config.toml and the GUI switch keep their filesystem meaning
  only.
- **Audit log**: each decision is appended to `<data-dir>/approvals.jsonl`
  (time, session, tool, operation, scope, risk, decision; no message content).
- The model is told not to set `confirm` itself and not to ask for permission
  in chat first; a denied or unavailable approval is reported as "nothing
  changed, do not retry".
- NestCafe and other branded overlays that render generic questions get the
  same request as a question with the three options.

## Thunderbird mail (`thunderbird_mail`)

- **Unknown arguments are rejected** before the bridge is called. Guesses such
  as `"query"` or `"unread": true` used to be ignored and silently widened a
  search or count to the whole folder; the error now names the real argument
  (`from`/`subject`/`text`, or `op: folders` for unread counts).
- **Read timeouts**: read operations wait 135 s, longer than the bridge's own
  120 s limit, so its "narrow the query" error arrives instead of a misleading
  "outcome unknown". Attachments and contacts use the same read limit.
- **Smaller results**: compact JSON without empty fields, so typical 10-20
  message answers stay inline.
- **Copy**: a destination folder id now selects its own account, so copying
  from Gmail into a folder of another account works. move/restore/import_msg
  refuse a destination in another account up front and point to copy. After a
  copy, a note names the folder holding the copies and warns against deleting
  in the copy source.
- **Folder administration never guesses the account**: `create_folder`
  requires `account` (or a parent folder id); `rename_folder`/`delete_folder`
  need a folder id or an explicit account. Before, a missing account could
  create a Gmail label instead of a Local Folders folder.
- An existing folder on `create_folder` is no longer reported as a blocker: the
  result says nothing changed and to continue with the existing folder id.
- Clearer folder-not-found/ambiguous errors, and updated tool description and
  NestCafe prompt (brand search via `from` plus `scope: "account"`, unread
  counts via `folders`, copy cleanup).

## Edits and answers

- **`patch_file` base_hash provenance**: a `base_hash` is honoured only when
  `patch_file` issued it earlier for that file. An invented hash is ignored with
  a note and the edit applies (the exact old text still guards against stale
  edits); an issued hash that no longer matches is still rejected.
- **`patch_file` ambiguity**: an ambiguous `old` text no longer suggests
  `expected_count`; the error lists each match (up to 6) with the lines above
  it so the right one can be chosen. A patch that changed several places
  reports every changed region instead of hiding the middle.
- **Missing targets**: the core prompt says "Missing file/target: say so and
  ask; never substitute another.", and every `not_found` from the read tools
  repeats it. Before, a model edited a different file and reported success.
- **Unverified success**: a final answer that claims passing checks while the
  last check failed, or when no command ran, gets a visible "SuperCli note".
  Compound shell lines and `node --test` count as checks; sentences that report
  a failure are not treated as claims. Worker reports are not annotated.
- **Edit loops**: when edits return to a version that already failed the same
  check with the same output, the check result says so and asks the model to
  change approach and re-read the failing assertion and the relevant code.
  After three such repeats SuperCli stops the edit loop and the model reports
  what it tried and the exact failure.

## Privacy and display

- **`tool_errors.log` no longer stores full tool arguments.** Each entry keeps
  the tool name and error class; the arguments are redacted and capped at 512
  bytes: file contents, patches, mail bodies, prompts and similar fields are
  replaced by their size and a short hash, secret-like keys (tokens,
  passwords, API keys, authorization, cookies) are masked, and secrets in URL
  query strings or `Bearer`/`password=` text are removed.
- **`no_color` works in the TUI.** `no_color = true` in config.toml, or a
  non-empty `NO_COLOR` environment variable, now turns off terminal colours
  (it was parsed but ignored).

## Development

- New agent eval suite: 26 tasks (coding in Go/Python/JS, repository
  understanding, precise edits, long compaction-forcing tasks, tool hygiene and
  web regressions) in `test/go/eval/agent-suite.json` with fixtures and
  reference solutions, graded by `internal/agenteval`. Run it with
  `go run ./cmd/supercli-evalsuite`; each run uses an isolated `--data-dir` and
  writes `report.json`/`report.md` with transcripts and a cost ledger. The
  fixtures are separate Go modules, so `go test ./...` does not build them.
- Tool registration is stricter: a tool must declare an argument schema (or
  explicitly opt out with `UncheckedArgs`), `ApprovalArg` requires `Approval`
  and a boolean schema property, and read-only tools cannot require approval.
  User tools without a schema get a JSON-object check instead of none.
- `internal/checkpoint` tests are deterministic under load: the output drain
  grace counts from the last read instead of process exit (this also removes
  false "WaitDelay" checkpoint errors with a slow consumer), native-process
  tests no longer run in parallel, and the slow native Windows tests are
  skipped with `-short`.
