# SuperCli 1.0.38 (draft)

Fixes for long orchestrations with many background workers in the web GUI,
and a calmer subscription usage panel. Polish notes follow the English ones.

## Before updating

- Back up your portable `supercli-data` directory and close other running
  copies before installing. The updater replaces the two executables, not
  private data, and a manual restart is required afterward.
- No configuration changes are required. `background_wake_max_auto` keeps
  its meaning as a loop guard, but now counts only automatic turns without
  progress and defaults to 20 (see below).

## The coordinator keeps pursuing the goal

Reported: with 30 parallel workers the coordinator "knew what to do and
didn't do it" — the composer said "Ready" while finished reports piled up,
until the user wrote again. A read-only copy of the conversation (version
1.0.37) showed exactly this, twice:

- After the user's message at 20:18 ("we have 25 free slots, use them") the
  user turn ended at 20:35; then ten automatic wake-up turns followed
  (20:35–20:51). Every one of them refilled freed worker slots (a `task`
  call) and added a goal note. The 11th report at 20:51:44 hit the cap of
  10 consecutive automatic turns, and every later report (20:51–21:17,
  about 20 of them) waited for the user's next message ("i jak?" at 21:17).
- The same happened after 21:17: the user turn and ten automatic turns
  (21:25–21:44), then held from 21:47 until the app was closed at 22:12,
  with about 20 more reports unanswered.

Changes:

- The cap counts only **consecutive automatic turns without progress**. A
  turn that starts or resumes a worker, changes a file, runs a command or
  updates the goal resets the count. A coordinator that keeps a worker pool
  full is never held; one that only reads reports and answers stops after
  20 such turns (default; `background_wake_max_auto`, now also in Settings →
  Modes: "Automatic wake-ups without progress").
- When reports are held, a banner above the composer says so ("Automatic
  wake-up paused (limit …) — N agent report(s) waiting") with a **Resume**
  button: one click continues without typing a message. The banner survives
  a refresh and disappears on resume, on the next message or when an
  automatic turn makes progress. Before, there was only a short toast.
- Every automatic turn repeats the user's latest instructions (up to three
  messages, compact, request-only) and asks the coordinator to keep pursuing
  them — e.g. "when an agent finishes, start a new one so the pool stays
  full" — together with the persisted goal state. The user no longer has to
  restate the goal after hundreds of worker reports pushed it far up the
  history.

## Worker cards say what really happens

Reported: "Worker 167 · code — Creating file · {path: …hunger_codec_tests.zig}"
showed "Creating file running · 2m11s · last activity 2m11s ago". In 1.0.37
that label starts only when the complete call is executing (the arguments
have been fully received), so it was not the model still streaming the file.
The file was created successfully (7078 bytes, no error), so neither the
path, a file lock nor the content size failed. The saved data has no
per-call timing for workers; the most likely wait is the checkpoint step
before the write: all workers of one coordinator turn share that turn's
checkpoint lock, a command of another worker may take a whole-workspace
snapshot under it, and the log shows checkpoint snapshots reading the
project's Zig build caches and hitting their 30 s limit.

- A file or command tool that waits for that lock now says so on the card
  and in the worker panel: "waiting for another agent's checkpoint snapshot".
- While the model is still writing a call (for example a large file), the
  card shows "model writing Creating file (7.2 KB) · 40s" with the streamed
  size growing, instead of "model thinking" with no visible progress
  (OpenAI-compatible and Responses/ChatGPT streams; calls from 1 KB). The server
  reports it as phase `args` with `phase_bytes` in `/api/workers`.
- A worker card rebuilt from history no longer shows "NaNmNaNs" when its
  report arrives.

## "Working in background" agrees with the worker panel

The composer badge counted the background workers of the conversation's
agent loops, the worker panel counted the workers it shows. In the
reported screenshot the panel said "working: 22" while the composer said
"Ready" without the badge. A full-app test with the same shape (idle
coordinator, several workers) shows the badge correctly, so the exact
mismatch was not reproduced; the badge now also counts the workers the panel
shows as running while the coordinator is idle, so both can no longer
disagree.

## Subscription usage updates in place

The "Subscription usage" block was deleted and rebuilt about once a second
while a reply streamed (and the usage/accounts panels were cleared to
"Loading…" on every refresh), so it flickered. All of these views now update
the existing elements in place: text, bar widths and attributes change, the
block stays.

The ChatGPT section could show a second bar "Window duration unknown ·
Reset: —": a placeholder window the backend returns on plans with a single
limit (0 % used, no duration, no reset). Such windows are hidden in the GUI,
the TUI and `/usage`; a second window that does carry data but no duration
is labelled "Additional limit".

## Tests

New tests (fake providers only): the wake-up cap ignores automatic turns with
progress and holds idle ones; Resume restores the budget and wakes held
reports; the hold notice updates its count without repeating; the user's goal
is repeated in every automatic turn; streamed tool-argument progress from the
OpenAI-compatible and Responses streams (throttled, never a call or
output); the worker `args` phase; checkpoint-lock wait reported as tool
progress; a full-app browser test of the user's case (workers writing a large
file, "Working in background (2)" with an idle coordinator, the held banner
surviving a refresh, one-click Resume); in-place updates of the usage panels
and hiding of the placeholder ChatGPT window.

# SuperCli 1.0.38 (PL, szkic)

Poprawki długich orkiestracji z wieloma agentami w tle w GUI oraz spokojniejszy
panel zużycia subskrypcji.

## Przed aktualizacją

- Zrób kopię przenośnego katalogu `supercli-data` i zamknij inne uruchomione
  kopie. Aktualizacja podmienia dwa pliki wykonywalne, nie dane prywatne. Po
  instalacji uruchom program ponownie ręcznie.
- Konfiguracja nie wymaga zmian. `background_wake_max_auto` nadal chroni przed
  pętlą, ale liczy tylko automatyczne tury bez postępu i domyślnie wynosi 20.

## Koordynator dalej realizuje cel

Zgłoszenie: przy 30 równoległych agentach koordynator „wiedział, co robić, i
tego nie zrobił” — pole wiadomości pokazywało „Gotowe”, a gotowe raporty się
zbierały, dopóki użytkownik czegoś nie napisał. Kopia rozmowy (tylko do
odczytu, wersja 1.0.37) pokazała dokładnie to, dwa razy:

- Po wiadomości o 20:18 („mamy 25 slotów wolnych, można je wykorzystać”)
  tura użytkownika skończyła się o 20:35, a potem przyszło dziesięć
  automatycznych tur (20:35–20:51). Każda uzupełniała zwolnione sloty
  (wywołanie `task`) i dopisywała notatkę do celu. Jedenasty raport o 20:51:44
  trafił w limit 10 automatycznych tur z rzędu i wszystkie kolejne (ok. 20,
  20:51–21:17) czekały na następną wiadomość („i jak?” o 21:17).
- To samo po 21:17: tura użytkownika i dziesięć automatycznych tur
  (21:25–21:44), potem wstrzymanie od 21:47 do zamknięcia aplikacji o 22:12,
  z ok. 20 raportami bez odpowiedzi.

Zmiany:

- Limit liczy tylko **kolejne automatyczne tury bez postępu**. Tura, która
  uruchamia lub wznawia agenta, zmienia plik, uruchamia polecenie albo
  aktualizuje cel, zeruje licznik. Koordynator utrzymujący pełną pulę agentów
  nigdy nie zostanie wstrzymany; taki, który tylko czyta raporty i odpowiada,
  zatrzyma się po 20 takich turach (domyślnie; `background_wake_max_auto`,
  teraz także w Ustawienia → Tryby: „Automatyczne wybudzenia bez postępu”).
- Gdy raporty są wstrzymane, nad polem wiadomości pojawia się pasek
  („Automatyczne wybudzanie wstrzymane (limit …) — czeka N raport(ów)
  agentów”) z przyciskiem **Wznów**: jedno kliknięcie kontynuuje bez pisania
  wiadomości. Pasek przetrwa odświeżenie i znika po wznowieniu, po następnej
  wiadomości albo gdy automatyczna tura zrobi postęp. Wcześniej był tylko
  krótki dymek.
- Każda automatyczna tura przypomina ostatnie polecenia użytkownika (do trzech
  wiadomości, zwięźle, tylko w zapytaniu) i prosi koordynatora o dalszą
  realizację — np. „jak zejdzie jakiś agent, rób na jego miejsce nowych, aby
  pula była zawsze maksymalna” — razem z zapisanym stanem celu. Nie trzeba
  powtarzać celu po setkach raportów, które odsunęły go daleko w historii.

## Karty agentów mówią, co się naprawdę dzieje

Zgłoszenie: „Worker 167 · code — Tworzenie pliku · {path: …hunger_codec_tests.zig}”
pokazywał „Tworzenie pliku działa · 2m11s · ostatnia aktywność 2m11s temu”.
W 1.0.37 ten napis pojawia się dopiero, gdy kompletne wywołanie jest
wykonywane (argumenty zostały już w całości odebrane), więc nie był to model
wciąż przesyłający plik. Plik utworzył się poprawnie (7078 bajtów, bez błędu), więc nie zawiodła
ścieżka, blokada pliku ani rozmiar treści. Zapisane dane nie mają czasów
pojedynczych wywołań agentów; najbardziej prawdopodobne oczekiwanie to krok
checkpointu przed zapisem: wszyscy agenci jednej tury koordynatora dzielą
blokadę checkpointu tej tury, polecenie innego agenta może pod nią robić
migawkę całego obszaru roboczego, a w logu migawki checkpointu czytające
katalogi pamięci podręcznej kompilacji Ziga przekraczały limit 30 s.

- Narzędzie plikowe lub polecenie czekające na tę blokadę pokazuje to na karcie
  i w panelu: „czeka na migawkę checkpointu innego agenta”.
- Gdy model wciąż pisze wywołanie (np. duży plik), karta pokazuje „model
  pisze: Tworzenie pliku (7.2 KB) · 40s” z rosnącym rozmiarem zamiast „model
  myśli” bez widocznego postępu (strumienie zgodne z OpenAI i Responses/ChatGPT,
  wywołania od 1 KB). Serwer zgłasza to jako fazę `args` z `phase_bytes` w
  `/api/workers`.
- Karta odbudowana z historii nie pokazuje już „NaNmNaNs”, gdy przychodzi
  raport jej agenta.

## „Pracuje w tle” zgadza się z panelem agentów

Plakietka w polu wiadomości liczyła agentów w tle z pętli rozmowy, a panel —
agentów, których pokazuje. Na zrzucie ze zgłoszenia panel miał „pracuje: 22”,
a pole wiadomości „Gotowe” bez plakietki. Test całej aplikacji o tym samym
układzie (bezczynny koordynator, kilku agentów) pokazuje plakietkę poprawnie,
więc dokładnej rozbieżności nie odtworzono; plakietka przy bezczynnym
koordynatorze liczy teraz także agentów, których panel pokazuje jako
pracujących, więc oba widoki nie mogą się już różnić.

## Zużycie subskrypcji aktualizuje się w miejscu

Blok „Zużycie subskrypcji” był usuwany i budowany od nowa mniej więcej co
sekundę podczas odpowiedzi (a panele zużycia i kont czyszczone do
„Ładowanie…” przy każdym odświeżeniu), więc migał. Teraz wszystkie te widoki
zmieniają istniejące elementy: tekst, szerokość pasków i atrybuty; blok
zostaje.

W sekcji ChatGPT mógł pojawiać się drugi pasek „Brak czasu trwania okna ·
Odnowienie: —”: okno zastępcze zwracane przez serwer przy planach z jednym
limitem (0 % zużycia, bez długości, bez odnowienia). Takie okna są ukryte w
GUI, TUI i `/usage`; drugie okno z danymi, ale bez długości, ma etykietę
„Limit dodatkowy”.

## Testy

Nowe testy (tylko atrapy dostawców): limit wybudzeń pomija automatyczne tury z
postępem i wstrzymuje bezczynne; Wznów przywraca budżet i budzi wstrzymane
raporty; powiadomienie o wstrzymaniu aktualizuje liczbę bez powtarzania; cel
użytkownika jest powtarzany w każdej automatycznej turze; postęp
przesyłanych argumentów narzędzia ze strumieni OpenAI i Responses
(dławiony, nigdy wywołanie ani treść); faza `args` agenta; oczekiwanie na
blokadę checkpointu jako postęp narzędzia; test całej aplikacji w przeglądarce
odwzorowujący zgłoszenie (agenci piszący duży plik, „Pracuje w tle (2)” przy
bezczynnym koordynatorze, pasek wstrzymania po odświeżeniu, Wznów jednym
kliknięciem); aktualizacja paneli zużycia w miejscu i ukrywanie zastępczego
okna ChatGPT.
