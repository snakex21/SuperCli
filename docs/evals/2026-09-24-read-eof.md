# Observed end of file in bounded reads — 2026-09-24

## Evidence and implementation

An archived USOS session contains a complete read of a 59-line source file, followed by a request for lines 200–300, an out-of-range error, and another read of lines 1–59. The successful first result had numbered lines but no explicit end-of-file marker. This is evidence of unnecessary reads, not proof that one missing marker caused every repetition. Other recent out-of-range errors involved incorrect shell line numbering and guessed offsets; this change does not fix those causes.

The local DeepSeek harness also exposes total-line metadata in its filesystem read presentation (packages/fs/tool-fs/src/read.ts and read-render.ts). SuperCLI now exposes only EOF actually observed by the requested read, avoiding a scan of the remaining file merely to count lines.

read_lines, read_context and each read_many item append a short marker such as `[end of file at line 59]` after reaching EOF. It works when the requested boundary coincides exactly with the last line, with or without a trailing newline. Detection reuses the existing buffered reader; at an empty buffer boundary it can require one further bounded refill (up to 32 KiB). It does not consume a whole following line, reopen the file or build a persistent file cache. Legacy library APIs and search windows do not request the extra EOF observation.

Partial ranges remain byte-identical. The renderer suppresses the marker if its total-output cap omits later lines. Existing per-line truncation warnings remain; reaching EOF does not imply that a very long line was fully displayed. Later generic/batch previews retain their omission markers and saved-output mechanisms. Out-of-range, empty-file, binary and cancellation errors keep their previous handling. EOF describes that read's observation; a later read checks the current file again.

No tool schema, instruction, helper inference, provider-specific path or Zen transport was changed. The marker costs 25 bytes for the 20-line fixture, only when EOF is reported. Existing output-compaction thresholds still apply, so a result close to a threshold may be compacted after adding metadata.

## Controlled live comparison

`scripts/read-eof/main.go` creates synthetic portable fixture directories and uses actual read_lines output as the result of a fixed initial read of lines 1–20. The model then determines the total entry count and RetryLimit. In exact-end the file contains 20 entries; the control has five further entries that must be read. Both contain RetryLimit=6842. The continuation has a six-step limit and 180-second context deadline.

The registry exposes read_lines and the automatically supplied saved-output tool. Shell tools are unavailable and cannot execute. Muse nevertheless attempted ctx_execute in both baseline scenarios and in the candidate control; these attempts failed dispatch. Some Muse reads also exceeded the existing 500-line cap by one. Therefore its larger baseline call count includes mistakes beyond checking EOF, and the full difference cannot be treated as a clean estimate for unrestricted sessions.

| Model / case | Model calls before → after | Attempted extra tools | Seconds before → after | Total input tokens before → after |
| --- | --- | --- | --- | --- |
| Qwen, exact end | 2 → 1 | 1 → 0 | 8.300 → 8.926 | 2001 → 930 |
| Muse, exact end | 5 → 1 | 4 → 0 | 24.354 → 6.088 | 8961 → 1229 |
| Qwen, more lines | 3 → 2 | 2 → 1 | 15.019 → 13.282 | 3274 → 2021 |
| Muse, more lines | 5 → 4 | 4 → 3 | 14.106 → 16.416 | 8352 → 6592 |

All eight answers were correct. Both candidate models read the extra lines in the control; neither assumed that the initial range was complete. Qwen baseline probed beyond EOF in both cases. With the marker it stopped after the complete initial read, or after retrieving the actual remaining lines.

The exact-end initial result grew from 479 to 504 bytes; the control's initial result stayed at 479 bytes. Models were qwen3.8-27b-uncensored on LM Studio and muse-spark-1.3-contributor-free on Zen, with reasoning requested at low. The first pair ran Qwen baseline and Muse candidate, the second reversed variants; different providers ran concurrently, and each model's two cases were sequential. Builds used a Go overlay to restore the five changed production files for the baseline.

These are one paired run per model/case, starting from a controlled initial read, not an unconstrained real task or a latency guarantee. Qwen exact-end and Muse control were slower despite fewer calls. Input totals include cached tokens and are not a billing estimate.

## Local overhead

Full read_lines tool calls on Windows / Ryzen 7 5800X3D, 500 iterations per sample, four samples per variant in before/after/after/before order:

| Fixture | Median before | Median after | Allocations/op |
| --- | --- | --- | --- |
| Read all 20 lines | 0.579 ms | 0.580 ms | 181 → 181 |
| Read first 20 of 20,000 lines | 0.596 ms | 0.590 ms | 181 → 181 |

Median allocated bytes were 42,691 → 42,759 and 42,754 → 42,784 respectively. Small allocator/timing variation dominates; no local speedup is claimed. The benchmark baseline restores the three tool call sites, using the legacy reader/renderer path. It excludes model inference.

## Validation

- The tool-level EOF regression fails against the prior call sites and passes after the change.
- Tests cover exact/past boundaries, LF/CRLF/no trailing newline, blank final or following lines, a huge following line and a 32 KiB buffer boundary.
- Instrumented readers verify bounded lookahead rather than scanning a 1 MiB remainder; file mutation tests reject stale EOF metadata.
- Tests cover all three read tools, partial-view byte parity, output/line omission markers, out-of-range errors and cancellation.
- Full `go test -timeout=90s ./...` and `go vet ./...` passed.

Local evidence is in `.tmp/read-eof/`: regression output, source snapshots/overlays, all live runs and comparison, benchmarks, full checks, release build/smoke results and installation verification.
