# Command outcomes survive context pruning

Date: 2026-09-26. Shared agent path; no provider, transport, model prompt or UI changes.

## Evidence

The fixed session snapshot contains 259 ctx_execute results, including 20 generated command_failed summaries. The old pruneMarker only decoded standalone JSON. Failure summaries (including timeout exit=124) therefore lost their exit code when selected for pruning. Complete successful JSON followed by the generated retained-output footer also lost its code. This proves a loss of evidence, not that these specific calls were pruned or that the model repeated them because of it.

## Change

Keep the command outcome in the existing short pruning marker. Read only the bounded first line generated by ctx_execute or the complete top-level JSON object. Strip an output footer only after validating its outer handle with the existing parser. Keep the read_output reference. Do not scan command stdout/stderr for statuses, infer success from a missing error, or guess a code from truncated JSON.

The fix adds no model calls, tool calls, file reads, persistent instructions or writes. Unpruned messages stay byte-identical. A pruned marker gains only its known exit_code field. Large cut JSON previews without a recoverable generated status still remain unknown; no success is fabricated.

## Validation

Red/green regression: five production-formatted cases (success, failure, timeout, Windows program-not-found, sandbox error) lost status before and retain it after. Native/thin provider-view fixtures retain timeout status after real pruning with one original tool invocation. Negative cases reject statuses embedded in log text, nested JSON, malformed framing and truncated JSON. Existing retrieval and pruning tests pass. No live-provider latency or saved-turn claim.
